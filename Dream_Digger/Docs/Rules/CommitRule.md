커밋 규칙 문서는 읽는 사람이 다음 내용을 알 수 있어야 한다.

1. 어느 단위로 커밋을 해야하는지 (범위)
2. 커밋 요약과 본문은 어떻게 작성해야 하는지 (관례)

---
## 1. 커밋 단위

- 작업을 되돌리기 쉬워야 한다.
- 한 번에 너무 많은 작업을 커밋하지 않는다.

---
## 2. 커밋 컨벤션

커밋의 요약 부분 맨 앞에는 항상 `타입`을 작성한다.

| 커밋 타입      | 목적                      |
| :--------- | ----------------------- |
| [Feat]     | 새로운 기능 구현 중 단계를 마쳤을 때   |
| [Docs]     | 문서 작업을 했을 때             |
| [Chore]    | 코드 사이 공백 제거나 폴더 배치 정리 등 |
| [Fix]      | 오류나 버그를 수정했을 때          |
| [Refactor] | 리팩토링 했을 때               |

요약에는 **'이 커밋 단위에서 무엇을 했는지' 알 수 있어야 한다**.

- 좋은 예시
	- `[Docs] 커밋 규칙 문서 추가`
	- `[Feat] 플레이어 좌우 이동 기능 구현`
	- `[Fix] 플레이어가 데미지를 입어도 체력이 줄지 않던 버그 수정`
- 나쁜 예시
	- `[Feat] 플레이어 좌우 이동` (무엇을 했는지 알 수 없음)
	- `[docs] 브랜치 규칙 문서` (타입 대소문자 구분)
	- `[Fix] GameManager.cs 내 필드 선언` (타입과 요약 불일치)
