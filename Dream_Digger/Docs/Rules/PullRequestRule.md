PR 규칙 문서는 읽는 사람이 다음 내용을 알 수 있어야 한다.

1. PR을 언제, 어떻게 올려야 하는지 (절차 및 시점)
2. 리뷰어가 해야 하는 것 (확인 및 병합)
3. PR을 어떤 단위로 나누고, Issue와 어떻게 연결하는지 (단위 및 연결)

---
## 1. PR을 올리는 기준

### 절차

1. 작업을 위해 생성한 브랜치에서 **목표로 한 작업이 끝나면 먼저 검토**한다.
	- Unity 콘솔에 오류가 없는지
	- 플레이 했을 때 해당 작업에 대한 이슈에 기재된
	  완료 기준과 그 검토 방법에 따라 문제가 없는지
	- 작업 내용을 전부 커밋 Push하고 남아있는게 없는지
	- 작업 해야할 씬 외에 다른 씬을 건드리지 않았는지
2. 모두 확인 했다면 PR을 생성한다.
   `현재 브랜치`에서 `main`으로 병합하는지 항상 확인한다.
3. `Reviewers` 에는 PR을 읽어야 하는 사람(협의된)을,
   `Assignees` 에는 담당자 자신을 지정한다.
4. PR 양식에 맞추어 내용을 채운다.

### 작업 단위

PR은 Issue의 「작업 계획 브리핑」에 세운 단계별 계획을 참고해서 나누어 올린다.

### Issue 연결

PR 본문에는 해당 작업의 Issue를 연결한다.

- Issue의 내용을 모두 마무리해서 더 작업할 브랜치가 없는 마지막 PR이라면,
  `Closes #이슈번호`로 연결해 PR이 병합될 때 Issue가 닫히게 한다.
- 마지막 PR이 아니라면 `#이슈번호`로만 연결해 Issue가 열린 상태로 남게 한다.

### 작성

PR의 제목에도 타입을 작성하되 현재 브랜치를 참고한다.

| 브랜치 타입   | PR 제목      |
| :------- | ---------- |
| feature  | [Feat]     |
| docs     | [Docs]     |
| fix      | [Fix]      |
| refactor | [Refactor] |

---
## 2. 리뷰어가 확인해야 하는 것

- PR에 지정된 리뷰어는 양식에 맞추어 `작성된 내용`과 `Files Changed`가 일치하는 지 확인한다.
- 내용을 다 읽고 코멘트를 남긴다.
- 리뷰어가 모두 확인 했다면 `merge`하여 `main`에 병합한다.
- 병합되어 더 이상 작업하지 않으므로 브랜치까지 삭제한다.

### 병합 커밋 메시지

`merge` 할 때 커밋 메시지는 아래 형식으로 작성한다.
병합 대상은 항상 `main`이다.

```
main << {GitHub 아이디}/{작업 브랜치 이름}

{PR 제목}
```

예시)
```
main << Makom64/feature-makom64-documents_setting

[Docs] PR 문서 분리 및 필요 문서 추가
```
