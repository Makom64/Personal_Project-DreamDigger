브랜치 규칙 문서는 읽는 사람이 다음과 같은 내용을 알 수 있어야 한다.

1. 브랜치를 어떻게 나눌 것인지 (관리)
2. 브랜치를 언제 생성해야 하는지 (시점)
3. 브랜치를 어떻게 생성해야 하는지 (생성)
4. 브랜치 명은 어떻게 작성해야 하는지 (명칭)

---
## 1. 브랜치 관리

절대 `main` 브랜치에서 작업하지 않는다.

브랜치를 나누는 기준과 목적은 다음과 같다.

| 브랜치 타입   | 목적                                                     |
| :------- | ------------------------------------------------------ |
| main     | 개발한 기능들과 작성한 문서들이 모이는 곳으로<br>언제든 오류 없이 구동 가능한 상태여야 한다. |
| feature  | 새로운 기능을 구현한다.                                          |
| docs     | 새로운 문서를 생성하거나 기존 문서를 수정한다.                             |
| fix      | 버그나 오류 발생 시 수정한다.                                      |
| refactor | 기존 구조를 개선한다.                                           |

PR이 승인되어 로컬에 남아있는 브랜치는
더 이상 작업하지 않으므로 삭제하도록 한다.

---
## 2. 브랜치 생성 (시점 및 방법)

브랜치는 **작업을 시작하기 전** 생성한다.

작업 중이던 브랜치가 없고, 지금 브랜치가 `main`이면,
목적에 맞는 브랜치를 만들고 개시(Publish)한 후 작업을 시작한다.

브랜치를 생성할 때는 Issue의 「작업 계획 브리핑」에서 나눈 단계를 참고한다.

---
## 3. 브랜치 이름

브랜치 이름은 이름만 보고서 **어떤 작업을 진행 중인지 알 수 있어야 한다**.

`<브랜치 타입>-<담당자 명>-<작업_내용_요약>` 으로 작성한다.
(담당자명은 개인 프로젝트이므로 GitHub ID `makom64`로 한다.)

- 읽기 어렵지 않도록 50 글자가 넘지 않도록 주의한다.
- 소문자로만 작성한다.
- 항목 구분은 `-`으로, 단어 사이 띄어쓰기는 `_`으로 한다.
- `.`은 처음과 마지막에 쓰지 않고, 2개를 연속으로 쓰지 않는다.

- 좋은 예시
	- `feature-makom64-playercontroller`
	- `refactor-seunghun_noh-monsterdata.cs`
- 나쁜 예시
	- `Feature-Makom64-PlayerController` (대문자 사용)
	- `docs-makom64-playercontroller_monobehaviour_script_develop`  (불필요하게 길다)
